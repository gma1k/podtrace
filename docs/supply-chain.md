# Supply chain security

Podtrace runs as a privileged DaemonSet and loads eBPF programs into your
kernel. That is a lot of trust to extend to a container image pulled off the
internet, so every release artifact ships with build provenance you can verify
yourself, and, for the image, enforce at admission time.

## What is attested

| Artifact | Signature | Provenance | Where the attestation lives |
|---|---|---|---|
| Container image `ghcr.io/gma1k/podtrace` | cosign keyless | SLSA v1 + BuildKit v0.2 | OCI referrer in GHCR, and GitHub |
| Helm chart `ghcr.io/gma1k/charts/podtrace` | cosign keyless | SLSA v1 | OCI referrer in GHCR, and GitHub |
| CLI tarballs `podtrace_*.tar.gz` | cosign keyless over `checksums.txt` | SLSA v1 | GitHub, plus `podtrace.sigstore.json` on the release |
| `quickstart.yaml`, `quickstart-demo.yaml` | — | SLSA v1 | GitHub, plus `quickstart.sigstore.json` on the release |
| Embedded BPF objects `podtrace.<arch>.bpf.o` | — | SLSA v1 | GitHub (verified in-pipeline, see below) |

All provenance is generated by [`actions/attest-build-provenance`][abp], signed
against the GitHub Actions OIDC identity of the release workflow, and recorded
in the public [Rekor][rekor] transparency log.

[abp]: https://github.com/actions/attest-build-provenance
[rekor]: https://search.sigstore.dev/

## What level this is, honestly

Podtrace release artifacts meet **SLSA v1.0 Build Level 2**: provenance exists,
describes the build, and is signed by a hosted build platform using key
material the build steps never see.

It is **not Build Level 3**. L3 additionally requires the provenance to be
generated in an environment isolated from the build itself, which on GitHub
Actions means the [slsa-framework/slsa-github-generator][slsa-gen] reusable
workflows. Podtrace does not use those today, mostly because the CLI build
needs a custom BPF toolchain and full kernel BTF that the SLSA Go builder
cannot provide.

Two related things that are easy to conflate and are worth stating plainly:

- **A cosign signature is not provenance.** It proves an identity signed the
  artifact. It does not describe how the artifact was built. Podtrace ships
  both; they answer different questions.
- **A `.sha256` file published next to the file it describes is not an
  integrity control.** Anyone who can replace one can replace the other. The
  `.sha256` companions on the quickstart manifests are kept for convenience
  and for scripts that already consume them — the attestation is the check
  that means something.

[slsa-gen]: https://github.com/slsa-framework/slsa-github-generator

## Verifying

All commands below need the [GitHub CLI][gh-cli] (`gh`). Each one fails
non-zero if verification does not pass, so they are safe to use in a script
with `set -e`.

[gh-cli]: https://cli.github.com/

### Container image

```bash
gh attestation verify oci://ghcr.io/gma1k/podtrace:latest \
  --repo gma1k/podtrace \
  --signer-workflow gma1k/podtrace/.github/workflows/release.yml
```

Add `--bundle-from-oci` to read the attestation from GHCR instead of the
GitHub API — useful from a network that can reach your registry but not
github.com. You must already be authenticated to the registry.

### Helm chart

```bash
gh attestation verify oci://ghcr.io/gma1k/charts/podtrace:latest \
  --repo gma1k/podtrace \
  --signer-workflow gma1k/podtrace/.github/workflows/release.yml
```

Run this before `helm install`. An admission controller cannot do it for you:
a chart is never admitted as a workload, so there is nothing for a webhook to
intercept.

### CLI tarball

```bash
cd "$(mktemp -d)"
curl -fsSLO https://github.com/gma1k/podtrace/releases/latest/download/podtrace_linux_amd64.tar.gz

gh attestation verify podtrace_linux_amd64.tar.gz \
  --repo gma1k/podtrace \
  --signer-workflow gma1k/podtrace/.github/workflows/release.yml
```

This checks the tarball directly. The older `cosign verify-blob` route through
`checksums.txt` still works and is documented in
[installation.md](installation.md); it takes two steps because the signature
covers the checksum file rather than the tarball.

For an air-gapped check, download `podtrace.sigstore.json` from the release and
pass `--bundle podtrace.sigstore.json`. The bundle is safe to carry alongside
the artifact: an attacker who swaps both still cannot produce a GitHub-signed
bundle for the substituted digest.

### Quickstart manifests

```bash
cd "$(mktemp -d)"
for f in quickstart.yaml quickstart.sigstore.json; do
  curl -fsSLO "https://github.com/gma1k/podtrace/releases/latest/download/$f"
done

gh attestation verify quickstart.yaml \
  --bundle quickstart.sigstore.json \
  --repo gma1k/podtrace \
  --signer-workflow gma1k/podtrace/.github/workflows/release.yml
```

### Inspecting what the provenance says

```bash
gh attestation verify oci://ghcr.io/gma1k/podtrace:latest \
  --repo gma1k/podtrace \
  --format json \
  --jq '.[].verificationResult.statement.predicate.buildDefinition.externalParameters.workflow'
```

That prints the repository, workflow path, and git ref the image was built
from. `resolvedDependencies` in the same predicate lists the source commit.

## Enforcing in a cluster

[`deploy/policies/kyverno-verify-podtrace.yaml`](../deploy/policies/kyverno-verify-podtrace.yaml)
is a Kyverno `ClusterPolicy` that refuses to admit a podtrace pod unless the
image carries both a keyless signature and SLSA v1 provenance naming this
repository, from a tag ref. It also rewrites the tag to the verified digest so
the kubelet cannot resolve a different image than the one that was checked.

```bash
kubectl apply -f deploy/policies/kyverno-verify-podtrace.yaml
```

Requires Kyverno v1.11 or later. Adjust the namespace selector if you install
podtrace somewhere other than `podtrace-system`.

One detail that determines whether this works at all: Kyverno reads
attestations as OCI referrers from the registry and cannot reach the GitHub
attestations API. The release workflow publishes image and chart provenance
with `push-to-registry: true` for that reason. If you mirror podtrace into a
private registry, copy the referrers too — `cosign copy` and `oras cp` both do
this, a plain `docker pull && docker push` does not.

## Provenance for the eBPF bytecode

The BPF objects are compiled in a separate matrix job from the jobs that embed
them, and travel between the two as a workflow artifact. That hand-off is the
one point where the bytecode podtrace loads into your kernel could be swapped
without anyone touching `bpf/`.

So the objects are attested where they are built, and the attestation is
verified where they are consumed: the `image` and `cli` jobs both refuse to
build if a staged object does not match a GitHub-signed bundle bound to the
same workflow, the same commit, and a GitHub-hosted runner. See
[`.github/actions/verify-bpf-objects`](../.github/actions/verify-bpf-objects/action.yml).

This does not make the compilation itself reproducible or hermetic — a
compromised toolchain would produce a bad object that is then faithfully
attested. It does mean the bytecode in a release can be traced back to a
specific workflow run and commit, which is what you want during an incident.

## Not covered

The OLM bundle submitted to [k8s-operatorhub/community-operators][ohub] has no
podtrace-generated provenance. The pipeline opens a pull request containing
`manifests/` and `metadata/`; OperatorHub builds and serves the resulting
bundle image, so there is no artifact for podtrace to attest. The operator
image the bundle references is attested normally, and that is the code that
actually runs.

[ohub]: https://github.com/k8s-operatorhub/community-operators
